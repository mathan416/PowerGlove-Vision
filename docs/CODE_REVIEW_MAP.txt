CURRENT SNAPSHOT AND VERIFIED WORK
----------------------------------
PowerGlove Vision 0.3.1 uses one shared recognition layer and two RetroPie input
paths. FCEUmm remains the complete standard-joypad path for every registered NES
game and for Super Glove Ball fallback. The separately named
lr-nestopia-powerglove core supplies native Super Glove Ball detection, Start,
continuous X/Y, and safe neutralization without changing stock Nestopia.

The current checkout includes release installers for UNO Q and RetroPie,
installation manifests, a paired Games registry service, personal gesture
tuning, sixteen Glove Academy lessons, the six-second launch guard, and the
versioned native-state bridge. The Help library exposes fourteen public PDFs;
the cabinet quick reference remains private.

Verification completed for this snapshot:
  - All 245 automated tests passed locally on September 5 after the native-core,
    installation, calibration, recognition, and documentation updates.
  - Documentation validation passed for all maintained Markdown and PDF files.
  - Fifteen project PDFs and the updated Console Guide PDFs were rendered and
    visually reviewed.
  - Super Glove Ball was tested through both FCEUmm and lr-nestopia-powerglove;
    Gun.Smoke was tested end to end through FCEUmm on the cabinet.

Automated and existing-machine checks do not replace a fresh-device installation
test. Native Z, roll, finger/action fields, and unverified native buttons remain
neutral. Keep FCEUmm available as the explicit rollback and complete-controls path.

START HERE
----------
1. README.md: understand the two-machine design and current limitations.
2. src/powerglove_vision/model.py: learn the data passed between components.
3. tracker.py -> gesture.py: follow landmarks into gestures and game inputs.
4. vision_app.py: see how camera, profiles, calibration and output cooperate.
5. transport.py -> receiver.py: follow an input from UNO Q to Linux uinput.
6. python/main.py -> control_server.py -> debug_server.py: distinguish the
   always-available website/supervisor from the restartable vision worker.
7. retropie_hook.py -> profile_control.py: follow a game launch back to UNO Q.
8. scripts/setup-machine.py and the systemd units: understand boot/deployment.
9. Read each matching test alongside the implementation, then pairing.py,
   resolver.py and the shutdown path with their trust boundaries in mind.
10. For documentation work, read help_content.py and scripts/build-docs-pdf.py
    together. They render the same Markdown with different parsing and layout
    rules. Use docs/CONTRIBUTING.md for the writing and publication workflow.

Except for the explicitly prefixed python/, scripts/ and retropie/ paths above,
the Python modules are under src/powerglove_vision/.

HOW THE PARTS CONNECT
---------------------
Camera -> tracker.py -> HandObservation -> gesture.py -> ControllerState
       -> transport.py -> UDP 55355 -> receiver.py -> uinput -> RetroArch/game

RetroPie runcommand hooks -> retropie_hook.py -> profile_control.py
       -> UDP 55356 -> vision worker changes the selected gesture profile

App Lab -> python/main.py (supervisor / runtime preparation)
       -> control_server.py (Dashboard, Learn, Help, Setup and APIs)
       -> vision_app.py (separate camera/tracking worker)
       -> debug_server.py (worker status and control requests)

matrix.py -> App Lab Bridge -> sketch/sketch.ino -> UNO Q LED matrix

resolver.py -> app-private Unix socket -> avahi-resolver-service.py
       -> host Avahi socket -> local-network hostname discovery

Confirmed web Shutdown -> fixed request file -> root-owned systemd path/service
       -> Linux halt request. The tested board can restart; do not infer power
          removal is safe from the website disappearing or matrix animation.

WHERE THE UI LIVES
------------------
There is no separate React/Vue frontend in this repository. The full pages and
browser JavaScript are embedded in control_server.py. debug_server.py has a
smaller worker diagnostic interface: it is not the complete application UI.
help_content.py selects/serves the allowed manuals and assets. Markdown is the
editable guide source; the PDFs and screenshots are generated artifacts.

IMPORTANT REVIEW QUESTIONS
--------------------------
- Does every path that disables tracking/output release held controls?
- Does Learn suppress gameplay packets and restore the selected mode afterward?
- Is a missing or invalid calibration handled clearly? Does a completed explicit
  calibration save atomically, and does storage failure remain visible?
- Does a saved neutral reference remain appropriate after the camera is moved?
- Are Start/Select held gestures distinct from continuous movement/action inputs?
- Are incoming packets authenticated, bounded and checked before uinput changes?
- Is UDP send success kept distinct from proof of receiver/game input?
- Does loss of traffic release buttons within the configured receiver timeout?
  Inspect receiver.py carefully: release currently follows socket.timeout, not
  an independent deadline measured from the last accepted packet. Review how
  repeated invalid or stale traffic interacts with that distinction.
- Does installation preserve private settings and existing cabinet hooks?
- Is the Avahi dependency installed on BOTH machines, with service boot enablement?
- Can App Lab recreate containers without losing the resolver service?
- Do shutdown and pairing APIs require the intended confirmations/safeguards?
- Are generated files excluded where necessary, and are third-party licenses and
  model checksums explicit? Inspect package exclusions rather than assuming
  everything in a working tree is appropriate for public distribution.
- Does the website accurately describe the currently running deployed version?

DOCUMENTATION AND PACKAGING REVIEW POINTERS
------------------------------------------
1. Read the overview for the project and common controls, the installation guide
   for the numbered setup journey, and the configuration reference for flags.
   Check that machine names, paths, required values, and expected results agree.
2. Follow a new installation from Git download to App Lab import, UNO Q host
   setup, RetroPie receiver installation, pairing, and actual game input. The
   supported UNO Q installer requires the exact application path shown above.
3. Compare Programs A-I and the dedicated game controls with gesture.py and
   test_gesture.py. Keep controller output distinct from its effect in a game.
4. When changing Markdown, check both Help and PDF output. The Help renderer
   expects each list item on one source line. PDF tables and code blocks need
   visual inspection; passing a link audit does not prove good pagination.
5. Check PDF links within a document and between documents separately. The
   renderer now creates destinations for section links; it does not translate
   every relative Markdown file link into a link to another PDF edition.
6. Keep rendering tests aligned with deliberate heading changes while retaining
   assertions for image coverage, navigation, and escaping. A title change
   caused the first CI run in this revision to fail; its corrected test passed.
7. Inspect package and deployment exclusions. The package builder copies the
   working directory with rsync, rather than exporting only Git-tracked files.
   This untracked notes file is not explicitly excluded and can enter a local
   ZIP. Untracked does not mean private or excluded from deployment. The public
   Help allowlist is a separate control and does not publish this file as a guide.

These are review pointers, not claims that a security audit was completed.

HOW TO READ AND TEST SAFELY
--------------------------
Start with static reading and the unit tests on the Mac. Do not run installers,

PROFILE SELECTION REPAIR (LOCAL WORK AFTER THE SNAPSHOT ABOVE)
------------------------------------------------------------
The installed UNO container originally published only TCP 8088 and 8443, so
RetroPie could not reach the worker's UDP 55356 profile listener. A signed off
request timed out before the fix and succeeded after UDP ingress was added.

New source to review:
  bricks/local/profile_control/brick_config.yaml
  bricks/local/profile_control/brick_compose.yaml
  scripts/profile-relay.py
  tests/test_profile_relay.py

The relay publishes UDP 55356 and forwards bounded exchanges over the private
Compose network. It has no token or private data mount. Authentication stays
in ProfileCommandServer. The App Lab manifest owns this brick, and a real
App Lab stop/start confirmed that the service and published port return.
The compatibility updater also adds the include for existing installations.

The worker previously acknowledged commands only after its vision loop handled
them. Camera startup could delay that response beyond the Pi's retry window.
The listener now sends a signed queue-admission acknowledgement immediately;
Dashboard remains the source for confirming the applied profile. Tests cover
this while no consumer is draining the queue. The hook reports queued versus
rejected accurately and handles missing configuration without blocking games.

Only two supported games originally matched this cabinet's archive filenames.
The remaining defaults covered .nes files, while the cabinet uses .7z. Exact
archive entries and the Sesame Street 123 filename spelling were added without
replacing existing local mappings. Matching remains exact and case-insensitive.

Live testing also exposed a USB camera call that blocked the vision loop. Camera
open, read, and close now use one serialized daemon worker; profile handling stays
in the responsive main loop. Active profile changes reuse the camera and tracker.
Regression tests verify that off applies while camera open or read is blocked.

Historical verification at this stage: all 113 software tests passed. On the actual Pi and UNO, installed
launch hooks selected Joust -> program_b, Gun.Smoke -> program_g, and Sesame
Street 123 -> program_f using the cabinet's .7z filenames. A temporary custom
mapping selected program_h. Every game-end hook selected off; an unregistered
game also selected off. Final state: off, with controller delivery stopped.
This exercised the real hooks and status endpoint, not gameplay or hand tracking.

These changes were later incorporated into the 0.3.0 source described at the top.
